# 트러블슈팅 기록

실제로 막혔던 지점과 원인, 그리고 코드에 남긴 대응입니다. 증상으로 찾을 수 있게 번호를 유지합니다.

### 1. Transformers를 설치했는데 계속 4.57.6으로 보이는 문제

모델 파일 다운로드와 Python 패키지 설치는 별개였습니다. 당시 커널이 이전 Transformers를 유지하여 모델 지원 버전 검사에서 중단됐습니다.
이 프로젝트의 Paddle+Qwen3.5 분석 노트북은 Transformers 5.3.0 이상을 요구하도록 구성했고,
해당 PC에는 5.17.0 wheel과 의존성을 준비했습니다. 모든 모델에 적용되는 보편적 최소 버전이라는 뜻은 아닙니다.

설치 셀에서 `INSTALL_PACKAGES=True`와 온라인/오프라인 소스를 설정해 **현재 커널의 Python**에 설치한 뒤,
커널을 재시작하고 `INSTALL_PACKAGES=False`로 되돌려 처음부터 실행합니다.
`sys.executable`, `transformers.__version__`, `transformers.__file__`로 실행 환경을 확인합니다.
다운로드 가이드의 wheel은 Windows Python 3.12 기준이므로 Colab에 그대로 설치하지 않습니다.

### 2. 오프라인 플래그 때문에 다운로드가 막히는 문제

분석용 `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `HF_DATASETS_OFFLINE` 설정이 다운로드와 충돌할 수 있었습니다.
다운로드 가이드는 offline 변수를 제거한 새 자식 프로세스를 사용하고, 분석 단계는 `local_files_only=True`를 사용합니다.
모델은 config·tokenizer·processor·가중치 shard를 함께 받으며 manifest의 크기와 shard 누락을 검증합니다.
파일 검증 성공은 GPU 로딩·추론 성공과 구분합니다.

### 3. RTX 5060 Ti와 오프라인 PyTorch 준비

베이스라인 준비 노트북에서 CUDA 12.8 빌드와 버전을 명시하여 wheel을 준비했습니다.
CPU 빌드 선택·OS/Python wheel 불일치가 생기지 않도록 다운로드 환경과 실행 환경을 맞춥니다.
설치 후 `torch.__version__`, `torch.cuda.is_available()`, GPU 이름을 확인합니다.
이 항목은 환경 준비 과정의 예방 조치이며, 현재 코드에서 CUDA 오류가 해결됐다는 일반 보장은 아닙니다.

### 4. OCR 픽셀 상한을 지정했는데 적용되지 않는 문제

프로젝트에서 확인한 Transformers 5.x 경로에서는 `apply_chat_template`의 `images_kwargs`만으로 기대한 상한이 적용되지 않았습니다.
`src/ocr_engine.py`는 실제 image processor의 `size` 또는 `min_pixels/max_pixels` 값을 수정합니다.
버전에 따른 dict/SizeDict/기존 속성 형태를 처리하고, 2048px 시험 이미지를 전처리하여 실제 토큰 격자에서 픽셀 수를 계산합니다.
설정값만 출력하지 않고 전후 픽셀 수가 증가하면서 상한 이내인지 검사합니다.

`2048 * 28 * 28 = 1,605,632`는 **전체 픽셀 수 상한**입니다. 모든 입력을 2048×2048로 만든다는 뜻이 아닙니다.
두 변이 모두 1500 미만인 입력은 2배 확대 후 프로세서가 상한에 맞게 처리합니다.
해상도를 낮추는 실험은 작은 글자·위치 정보 손실을 함께 평가해야 합니다.

### 5. OCR이 오래 걸리는 문제와 KV cache

모델 설정에는 `use_cache=False`가 남아 있지만 현재 생성 호출은 `use_cache=True`로 명시합니다.
이미 적용된 코드의 장시간 처리를 다시 cache 미사용 탓으로 단정하지 않습니다.
Spotting은 글자와 좌표를 순차 생성하므로 출력 길이와 단일 이미지 처리도 비용에 영향을 줍니다.

기존 작업 기록에서 로컬 캐시 254건의 평균은 약 9.05초/장이었고, 52건(약 20.5%)이 1,024토큰 상한에 도달했습니다.
이를 6,714장으로 환산한 약 16.9시간은 **로컬 일부 샘플 추정**이며 A100 실측값이 아닙니다.
사용자가 보고한 A100 약 15시간 및 노트북의 T4 안내 문구도 최종 완료 시간과 구분합니다.

```text
예상 남은 시간(시간) = 남은 이미지 수 × 현재 장당 처리 시간(초) / 3600
```

### 6. 토큰 제한과 보정 측정

512토큰 A 실험에서 OCR 잘림 비율 23.81%를 기록하여, 이후 OCR 캐시에는 기본 1,024토큰을 사용했습니다.
`RUN_CALIBRATION=True`는 대표 16장으로 `Spotting:`과 `OCR:`를 최대 3,072토큰까지 비교합니다.
이 보정 결과는 완료 캐시에 추가하지 않으므로, 단순 재개 시에는 `False`로 둡니다.

저장된 Spotting 보정 로그는 평균 8.24초/장, 최대 길이 도달 1/16을 기록했습니다.
로그의 토큰 한도별 커버율은 이 16장 표본의 길이 기준 추정이며 OCR 정확도나 전체 데이터 보장치가 아닙니다.
실제 상한에 닿은 출력이 있어 3,072 이하라고 모든 이미지의 전사가 완료됐다고 볼 수도 없습니다.
현재 로컬 배치 코드는 먼저 512토큰까지 생성하고 잘린 이미지만 설정 상한으로 다시 생성합니다.
전체 1,024토큰 일괄 생성보다 얼마나 빠른지는 동일 샘플로 별도 측정해야 합니다.

### 7. A100인데 GPU 메모리를 적게 쓰는 문제

메모리 점유량과 연산 사용률은 다릅니다. 한 장씩 추론하면 GPU 메모리가 남아도 순차 생성 때문에 시간이 길 수 있습니다.
A100 노트북은 남은 이미지에서 최대 16장을 뽑아 배치 1/2/4/8을 비교하고,
샘플 출력이 단일 처리와 일치하는 후보 중 장당 시간이 가장 짧은 값을 선택하도록 구현했습니다.
전체 데이터에 대한 출력 동일성과 개선 배수는 보장하지 않으며, A100 최종 벤치마크 결과는 아직 확인하지 못했습니다.

로컬 노트북은 별도의 방식입니다. 배치 4로 시작하고 OOM이면 보통 4→2→1로 줄이며,
여유 메모리가 있다고 배치를 자동으로 키우거나 단일 처리와 결과를 자동 비교하지 않습니다.
배치가 커도 긴 출력에 따른 대기 때문에 4배 빨라진다고 볼 수 없고, 수치 연산 차이로 결과도 일부 달라질 수 있습니다.
현재 작업은 추론 배치이며 모델 가중치를 학습·갱신하지 않습니다.

### 8. 배치 padding 경고와 종료 토큰 처리

A100 초기 버전에서 `padding=True` 전달 방식에 대한 `processor_kwargs` 경고가 반복됐습니다.
현재 코드는 `apply_chat_template` 시그니처에 따라 `processor_kwargs={"padding": True}` 또는 직접 padding을 전달합니다.
left padding을 사용하고 입력 길이를 제외한 생성 부분에서 EOS까지 잘라 이미지별 토큰 수와 잘림 상태를 계산합니다.
입력·출력 개수가 다르면 중단합니다. 벤치마크 진행 표시도 추가했습니다.
당시 HF_TOKEN·deprecated·rope_parameters·tied weights 경고만으로 실행 실패라고 판단하지 않았습니다.
새 오류는 마지막 traceback과 실제 진행 여부를 함께 확인해야 합니다.

### 9. 오래 실행한 OCR을 다음 날 이어서 실행하기

`durable_append`가 이미지별 JSONL 기록 후 flush와 fsync를 수행합니다.
진행 요약은 임시 JSON 작성 후 교체하며, **완료 여부의 기준은 progress.json이 아니라 실제 JSONL의 유효 ID**입니다.
재개 시 ID를 다시 읽어 완료 이미지를 제외하고, 모델·프롬프트·토큰 상한·픽셀 설정 등의 메타데이터를 검사합니다.
행 수는 LIMIT 변경을 허용하지만 다른 설정이 바뀌면 기존 캐시와 섞지 않도록 중단합니다.

```python
BATCH_SIZE = 4
RUN_HOURS = None            # 시간 제한 없이 실행
MAX_IMAGES_PER_RUN = None  # 장수 제한 없이 실행
RUN_CALIBRATION = False    # 기존 설정으로 이어갈 때
```

종료 전 실행 중지 후 `저장 완료`를 확인합니다. 시간 제한은 배치 사이에서 검사하므로 마지막 배치 시간만큼 초과할 수 있습니다.
배치 계산 중 강제 종료하면 아직 저장되지 않은 결과는 다음 실행에서 재처리합니다.
자동 중지는 OCR 작업만 멈추며 컴퓨터를 종료하지 않습니다.

### 10. 같은 ID가 중복되어 재개가 실패한 문제

당시 `train_0009.jpg`~`train_0012.jpg` 4건은 OCR 결과가 같고 시간 값만 달랐습니다.
복구 코드는 `seconds`, `batch_seconds`, `batch_size`, `seconds_kind`를 제외한 결과가 같을 때만 중복을 제거합니다.
원본 `.recovery-*.bak`를 만든 뒤 정리하며, OCR 내용이 다르면 자동 선택하지 않고 오류를 냅니다.
중간 줄 손상도 임의 삭제하지 않습니다. 마지막 미완성 줄은 백업 후 재처리하고,
마지막 JSON이 정상인데 개행만 없으면 구분용 개행을 추가합니다.

### 11. Windows PermissionError / WinError 5

캐시를 정리한 임시 파일로 `os.replace`하는 과정에서 액세스 거부가 발생했습니다.
다른 실행을 중지하고 커널을 재시작하는 절차를 안내했으나 교체가 계속 거부되어,
원본을 보존한 채 중복을 정리한 **train_spotting_local_resume.jsonl**을 별도로 만들었습니다.
전환 시점에는 완료 477장 / 남음 6,237장이었으며 이후 계속 증가했습니다. 파일 잠금의 정확한 주체는 확정하지 못했습니다.

현재 노트북은 해당 이어하기 파일이 있으면 우선 선택합니다.
후속 분석·복사 시 오래된 `train_spotting.jsonl`만 가져오지 말고 실제 `OUT_PATH`를 확인해야 합니다.
같은 캐시 파일에 두 프로세스가 동시에 쓰지 않도록 합니다.

### 12. 수정한 함수가 반영되지 않거나 SPLIT이 없다는 문제

파일을 고쳐도 Jupyter 메모리에는 이전 함수가 남아 있을 수 있어 `importlib.reload` 후 필요한 함수를 다시 import하도록 보강했습니다.
커널을 재시작한 뒤 재개 셀만 실행하면 `SPLIT` 등 파라미터가 없어 실패할 수 있습니다.
노트북의 **제목 기준 1. 라이브러리 → 2. 파라미터 → 3. 데이터 로드·검증 → 5. 이어하기 준비 → 6. OCR 실행** 순서로 실행합니다.
4번 보정 측정은 재개에 필수 단계가 아닙니다. 셀 재실행 자체가 완료 캐시를 삭제하지 않습니다.

### 13. Colab 세션 종료와 Drive 저장

Colab 노트북은 로컬 처리와 Drive 보관을 구분합니다. 런타임을 삭제하기 전에 정상 중지하고 Drive에 진행분이 저장됐는지 확인합니다.
A100 버전으로 바꿀 때도 기존 ZIP_PATH·DRIVE_BASE와 완료 캐시를 이어받습니다.
세션 메모리에만 남은 진행 상태를 완료 결과로 간주하지 않습니다.

### 14. 파일 분류 후 import와 상대 경로 문제

노트북을 하위 폴더로 옮긴 뒤에도 첫 코드 셀에서 저장소 루트를 찾아 `src/`를 import 경로에 추가하도록 보완했습니다.
실행·생성 도구의 대상 노트북 경로와 테스트의 모듈 경로도 함께 수정했습니다.
`run_nb.py`는 전달받은 노트북 경로를 먼저 절대 경로로 해석한 뒤 저장소 루트에서 실행합니다.
Colab 전용 노트북의 내용은 이동 전 그대로 보존했습니다.

### 15. 배치 크기를 1로 줄였더니 더 느려진 문제

로컬 캐시 기록에서 batch_size=4 구간 1,040장은 장당 8.64초, 생성 길이를 보정한 초당 토큰은 40.0이었습니다.
같은 파일의 batch_size=1 구간 18장은 장당 42.40초, 초당 토큰 20.7이었습니다.
생성 길이 편차 때문에 배치가 불리할 것이라는 예상과 반대로, 이 환경에서는 배치 4가 더 빨랐습니다.

다만 batch_size=1 표본은 18장뿐이고, 그 구간에 실험 C 추론이 같은 GPU에서 동시에 실행되고 있었습니다.
해당 구간 안에서도 뒤로 갈수록 초당 토큰이 30~50에서 6~12로 떨어집니다.
따라서 **42.40초라는 값은 경합이 섞인 수치**이며 배치 크기만의 효과로 볼 수 없습니다.
배치 크기를 비교하려면 다른 GPU 작업이 없는 상태에서 같은 이미지 집합으로 다시 측정해야 합니다.

### 16. 순차 처리한 앞부분만으로 평가해도 되는지

train OCR은 `train.csv` 순서대로 진행하므로 완료분은 인덱스 0부터 연속된 앞부분입니다.
1,698장 완료 시점에 완료분과 미완료분을 비교한 결과입니다.

| 항목 | 완료분 1,698 | 미완료 5,016 |
| --- | ---: | ---: |
| 정답 a/b/c/d 비율 | .246/.241/.268/.245 | .256/.246/.251/.247 |
| 텍스트 판독형 질문 | 65.4% | 65.7% |
| 시각 속성형 질문 | 10.4% | 12.6% |
| 질문 길이 / 선지 길이 | 31.7 / 9.3 | 31.9 / 8.8 |

행 순서가 특정 기준으로 정렬돼 있지 않아 앞에서 자른 표본이 크게 치우치지 않았습니다.
다만 시각 속성형 질문이 2.2%p 적으므로 OCR 기반 조건의 점수가 약간 후하게 나올 수 있습니다.
질문 유형 분류는 키워드 휴리스틱이며 정확한 라벨이 아닙니다.

학습을 하지 않으므로 고전적 과적합은 없습니다. 대신 같은 표본으로 프롬프트를 반복 선택하면
그 표본의 잡음을 고르게 됩니다. 정확도 90% 기준 95% 신뢰구간은 n=672에서 약 ±2.3%p,
n=2,000에서 약 ±1.3%p이므로 이보다 작은 차이는 구분하지 않습니다.
프롬프트 탐색용과 최종 확인용 집합을 미리 분리하는 편이 안전합니다.

### 17. CoT를 켤 때 파서와 지시문 충돌

`common_eval.parse_choice`는 정리 후 출력이 정확히 a~d 한 글자일 때만 인정합니다.
CoT 출력은 문장이므로 이 파서를 그대로 쓰면 전부 INVALID가 됩니다.
`parse_choice_cot`는 `정답: x` 형태를 **뒤에서부터** 찾고, 없으면 마지막 비어 있지 않은 줄에서
단독 선지 하나만 있을 때 채택합니다. 한 줄에 여러 선지가 있으면 INVALID로 둡니다.

프롬프트도 함께 바꿔야 합니다. 기존 마지막 줄은 "한 글자만 답하세요"이므로
CoT 지시를 덧붙이면 두 지시가 충돌합니다. `make_prompt(row, cot=True)`는 질문·선지 본문을
그대로 두고 **마지막 지시문 한 줄만** 교체합니다. 자기 테스트에서 두 모드의 본문 동일성을 확인합니다.

E2 실행 후에는 `invalid_rate`와 `answer_truncated_rate`를 먼저 확인합니다.
INVALID가 많으면 형식 미준수를, 잘림이 많으면 512토큰 내 미완결을 측정한 것이므로
정확도를 CoT의 효과로 해석할 수 없습니다.

### 18. Qwen3.5-9B 가중치 shard 누락

다운로드 중 `downloads/models/Qwen3.5-9B/`에 config·tokenizer만 있고
`model.safetensors.index.json`이 요구하는 shard 4개(합계 18.0 GiB)가 없는 상태가 관찰됐습니다.
같은 시점 폴더 용량은 31 GB였는데, 대부분이 `.cache/huggingface/download/*.incomplete`
중단 조각이었습니다. 폴더 용량만으로 다운로드 완료를 판단하지 않습니다.

E1/E2 노트북은 첫 셀에서 index가 요구하는 shard 파일의 실제 존재 여부를 검사하고
누락 시 중단합니다. 또한 9B는 bf16 기준 18.0 GiB이므로 16 GiB GPU에서는 4bit가 필요합니다.
B가 비4bit였으므로 `E1 − B`에는 모델 크기와 양자화 차이가 함께 들어 있습니다.

### 19. Colab에서 비공개 저장소 clone이 실패하는 문제

Colab 노트북이 `src/common_eval.py`를 쓰려고 `git clone`을 하면
`could not read Username for 'https://github.com'`으로 멈춥니다. 저장소가 비공개라
Colab에 자격 증명이 없기 때문입니다. 대화형 입력을 기다리며 셀이 멈춘 것처럼 보입니다.

E1/E2 Colab 노트북은 세 단계로 찾습니다. ① Drive 사본

### 20. CoT에서는 a~d 로짓 폴백을 그대로 쓸 수 없는 문제

E1은 파서가 실패하면 a~d 토큰의 로짓을 비교해 채웁니다. 특정 글자를 기본값으로 두면
분포가 무너지기 때문입니다(기존 베이스라인이 `return "a"`를 써서 a가 42%가 됐습니다).

**이 폴백을 CoT 입력에 그대로 옮기면 안 됩니다.** CoT 프롬프트에서 모델이 낼 다음 토큰은
선지 글자가 아니라 설명의 첫 글자입니다. 그 자리에서 a~d 로짓을 비교하는 것은
근거 없는 값을 고르는 것과 같습니다.

E2 Colab은 2단으로 바꿨습니다. ① 같은 이미지를 **E1과 글자 단위로 같은 비-CoT 프롬프트**로
24토큰 재질의 ② 그래도 INVALID면 **그 비-CoT 입력 위에서** 로짓을 비교합니다.
로컬 E2는 폴백이 없어 INVALID 1건이 그대로 오답이 됐는데, 이 경로에서는 0건이 됩니다.

토큰 상한에 걸린 출력도 폴백으로 넘깁니다(`RETRY_ON_TRUNCATED`). 잘린 추론은 결론에
도달하지 못한 것이라, 마지막 줄에 우연히 남은 글자를 최종 답으로 삼을 근거가 없습니다.
로컬 검증에서 512토큰에 걸린 2건은 2건 모두 오답이었습니다.

`verify_e2_colab_notebook.py`가 이 네 분기(정상 / INVALID→재질의 / INVALID→로짓 / 잘림→폴백)를
GPU 없이 모두 태워 보고, 로짓 폴백이 CoT 입력 위에서 호출되면 실패하도록 단언을 걸어 두었습니다.

### 21. 전사 프롬프트가 같은 구절을 반복하며 토큰을 소진하는 문제

E3 1단계에서 이미지의 글자를 그대로 옮기게 하면 일부 문항에서 같은 구절이 반복됩니다.
햇반 용기를 찍은 문항은 `햇반 김치국밥`을 18회 반복해 160토큰을 전부 썼습니다.
672문항 중 12건(1.79%)이 상한에 걸렸고, 그 12건의 정확도는 0.750으로 전체 0.942보다 낮습니다.

greedy decoding에서 반복 구간에 빠지는 알려진 현상입니다. 반복 페널티나 상한 조정으로
완화할 수 있지만, 그러면 E1과 디코딩 조건이 달라져 `E3 - E1` 비교가 깨집니다.
그래서 E3에서는 조건을 유지하고 `transcript_truncated`로 표시만 남겼습니다.
분석에서 이 12건을 따로 떼어 볼 수 있게 하는 쪽을 택했습니다.

전사 길이도 함께 보세요. 평균 19.1토큰인데 5토큰 이하가 34건입니다.
그쪽 정확도는 0.941로 전체와 같아, 짧은 전사 자체는 문제가 아니었습니다.

### 22. 중간 전사를 만들면 2단계가 그것을 과신하는 문제

2단계 구조에서는 오답이 두 갈래로 나뉩니다. E3 오답 39건은 읽기 실패 26건과
**대조 실패 13건**으로 갈렸습니다. 대조 실패는 1단계가 정답 텍스트를 정확히 읽어냈는데
2단계가 다른 선지를 고른 경우입니다.

예를 들어 전화번호 문항은 `865-3006·865-3008`로 정확히 전사하고도 `865-3006`만 있는
선지를 골랐습니다. 전사문이 프롬프트 앞머리에 놓이면 그럴듯한 권위를 갖게 되고,
2단계는 이미지를 다시 확인하기보다 전사문 요약에 기대는 경향을 보입니다.

1단계가 정답 텍스트를 읽어낸 389건 중 2단계가 96.7%를 맞췄으므로 대조 자체는 잘 돕니다.
다만 오답의 3분의 1이 여기서 나오므로, 2단계 지시문에 "전사문과 글자가 가장 정확히
일치하는 선지를 고르라"를 명시하는 개선 여지가 남아 있습니다. 상한은 +1.9%p입니다.

### 23. 27B를 16 GiB GPU에 올리면 오프로딩 때문에 느린 문제

27B를 4bit로 양자화해도 임베딩과 lm_head(각 약 2.5 GiB, 양자화 대상 아님)까지 GPU에 두면 16 GiB를 넘습니다.
이 둘만 `device_map`으로 CPU에 두면 들어가지만, accelerate 기본 오프로딩은 forward마다 가중치를 GPU로 복사해
9B로 시험했을 때도 문항당 0.8초 → 3.8초로 느려졌습니다.

임베딩은 조회뿐이고 lm_head는 생성 중 마지막 토큰 하나만 계산하므로, 오프로딩 훅을 떼고 **CPU에서 직접 계산한 뒤
결과만 GPU로 보내게** 바꿨습니다(`vlm_runtime.execute_on_cpu`). 9B에서 1.3초로 줄었고 a~d 로그확률은 소수점까지 같았습니다.
27B는 이 방식으로 peak 12.5 GiB, 문항당 2.06초였습니다.

### 24. Colab에서 vLLM 설치 뒤 transformers import가 실패하는 문제

`pip install vllm`이 torch를 CUDA 13 빌드로 바꾸는데, Colab에 원래 있던 torchaudio는 CUDA 12.8 빌드로 남습니다.
transformers는 torchaudio가 있으면 자동으로 불러오다가 `PyTorch and TorchAudio were compiled with different CUDA versions`로 멈춥니다.
이 작업에는 torchaudio가 필요 없으므로 설치 셀에서 지우고(`pip uninstall -y torchaudio`), **세션을 다시 시작한 뒤** 2번 셀부터 실행합니다.
이미 한 번 import가 실패한 세션에서는 캐시가 꼬여 재시작이 필요합니다.

### 25. Colab에서 LoRA를 붙일 때 torchao 버전 오류가 나는 문제

`get_peft_model`에서 `Found an incompatible version of torchao. Found version 0.10.0, but only versions above 0.16.0 are supported`가 납니다.
peft는 torchao가 설치돼 있으면 버전을 검사하는데 Colab 기본 torchao가 0.10입니다. 역시 필요 없는 패키지라 설치 셀에서 지웁니다.
E7 노트북의 import 셀은 torchaudio·torchao가 남아 있으면 해결 방법을 알려주며 멈춥니다.

### 26. 로컬 GPU가 "GPU is lost"로 사라지는 문제

Jupyter 커널 3개가 동시에 떠 있던 중(27B와 9B가 각각 올라간 상태) PCIe 링크 오류(WHEA 17)가 연달아 찍히고
드라이버가 GPU를 잃었습니다(nvlddmkm 153). 이후 모든 CUDA 호출이 `cudaErrorMemoryAllocation`으로 실패하는데,
메모리 부족이 원인이 아니라 결과입니다. `nvidia-smi`가 "GPU is lost. Reboot the system"을 보고합니다.

**"다시 시작"으로만 복구됩니다.** 빠른 시작이 켜진 Windows에서 "시스템 종료" 후 전원을 켜면 드라이버 상태가 복원돼
그대로입니다(부팅 시각이 바뀌지 않음). GPU 작업은 한 번에 하나만 돌리고, 쓰지 않는 커널은 닫으세요.
재발하면 보조전원 케이블, PCIe 속도(Gen4 고정), 드라이버를 확인합니다.

### 27. LoRA를 합친 모델에서 mtp 가중치가 빠지는 문제

`merge_and_unload()` 후 `save_pretrained`로 저장하면 원본에 있던 `mtp.*`(다중 토큰 예측 층) 가중치가 빠집니다.
transformers가 이 층을 불러오지 않기 때문입니다. 일반 추론에는 쓰이지 않지만 config에는 남아 있어
vLLM이 찾을 수 있으므로, 원본에서 그대로 복사해 가중치 이름 집합을 원본과 같게 맞춥니다(`qlora.copy_missing_weights`).
